# Insurance Adequacy Engine — Specification

Version: 1.0
Date: Day 1
Status: Draft

---

## 1. Overview

The Insurance Adequacy Engine is a backend system that analyzes an individual's
insurance protection needs across multiple product types (term life, health,
accident, disability), evaluates their existing coverage, identifies gaps,
and produces a budget-constrained plan to close those gaps — with plain-English
explanations generated by an LLM layer that falls back to templates when
the LLM is unavailable.

The engine targets the Indian market specifically, incorporating Indian tax
regime rules (Section 80C/80D), city-tier-adjusted medical cost benchmarks,
and awareness of common Indian insurance mis-selling patterns
(ULIP/endowment products).

---

## 2. Problem Statement

India has a structural insurance protection gap:

- Insurance penetration is 3.7% of GDP, roughly half the global average.
- About 60% of Indians have no health insurance.
- Among those who do, most carry inadequate cover (3-5 lakh policies in
  cities where a single major hospitalization costs 5-10 lakh).
- The average term life policy is 30-50 lakh, while the actuarially computed
  need (via HLV) for a mid-career professional often exceeds 1.5-2.5 crore.
- Only 23% of Indian adults understand basic insurance concepts.
- Existing free tools give crude single-product answers ("buy 15x your income")
  that ignore existing policies, budget constraints, city-specific medical
  costs, and the post-2024 tax regime reality.

The gap exists because insurance is sold (not bought), financial literacy is
low, and existing tools are either crude or biased toward selling specific
products.

---

## 3. Users and Stakeholders

### 3.1 Primary User: Individual Consumer

A 25-55 year old Indian with financial responsibilities (dependents, debts,
or both). They want to know:
- How much coverage do I actually need, across which product types?
- Is my existing coverage adequate, or am I over/under-insured?
- If I have a limited monthly budget, what should I buy first?
- Explain this to me in language I understand.

### 3.2 Secondary Stakeholders

The engine is platform-agnostic. The same backend can serve:
- Insurance aggregators (as a lead-capture and trust-building tool)
- Financial advisors (as a client assessment tool)
- Banks and wealth-tech apps (as a cross-sell intelligence feature)
- Corporate HR teams (for employee benefit planning)
- Regulator-aligned initiatives (IRDAI's protection gap mission)

The engine does not pick a business model. It produces assessments.
Deployment context determines monetization.

## 4. Functional Requirements

### FR-1: Accept User Profile Input

The system must accept the following inputs:

Personal information:
- Age (integer, 18-80)
- Gender (male/female/other — affects term insurance pricing)
- City tier (1/2/3 — affects health cover recommendations)
- Annual income (in rupees)
- Monthly expenses (personal, excluding dependents)
- Monthly insurance budget (the hard constraint for recommendations)
- Tax regime (old/new — affects effective premium calculations)

Family composition:
- Spouse (yes/no, with age and income if yes)
- Children (count, with ages)
- Dependent parents (count, with ages)

Financial obligations:
- Outstanding home loan balance and remaining tenure
- Outstanding vehicle/personal loan balances
- Planned future expenses (children's education, marriages — with
  estimated amounts and target years)

Existing insurance policies (zero or more):
- Policy type (term/endowment/ULIP/health/accident/disability)
- Sum assured
- Annual premium paid
- Policy start year
- Policy maturity year (for endowment/ULIP)

Existing financial assets:
- Total investable assets (savings, FDs, mutual funds, etc.)
- EPF/PPF balance

### FR-2: Compute Life Insurance Adequacy

The system must compute the recommended life cover using two frameworks
and return the higher of the two:

Framework A — Human Life Value (HLV), Income Replacement Method:
- Formula: (Annual Income - Personal Expenses) x Working Years Remaining
- Discounted to present value at an inflation-adjusted rate
- Discount rate: 6% default (within IRDAI's 5-8% guidance range)
- Working years = retirement age (60) minus current age
- This represents the present value of income the family would lose

Framework B — Need-Based Analysis (NBA):
- Sum of: outstanding liabilities + future obligations (education,
  marriages) + emergency corpus (6 months of household expenses) +
  surviving spouse retirement corpus
- Minus: existing investable assets + EPF/PPF balance
- This represents the specific financial obligations that need funding

Final recommendation: max(HLV, NBA)

Why both: HLV captures income replacement. NBA captures obligation
coverage. For most middle-class Indians with home loans, NBA exceeds
HLV because the loan balance dominates. Using both and taking the
max is what certified financial planners actually do.

The system must also show the common "10x income" heuristic for comparison,
and explain why it may be inaccurate for the user's specific situation.

### FR-3: Compute Health Insurance Adequacy

The system must recommend health cover based on city tier, family size,
and age — NOT as a percentage of income.

Minimum floors (individual):
- Tier-1 metro (Delhi, Mumbai, Bangalore, Chennai, Kolkata, Hyderabad):
  10 lakh minimum, 25 lakh recommended
- Tier-2 city: 10 lakh recommended
- Tier-3 city: 5 lakh minimum, 10 lakh recommended

Adjustments:
- Family floater: base + 5 lakh per additional family member
  (simplified heuristic)
- Age adjustment: for users above 45, add 20% to the recommendation
  (higher hospitalization probability)
- Existing conditions: if the user reports any, add 25% buffer
  (simplified heuristic — real underwriting is more complex)

Medical inflation context: the system must note that healthcare costs
in India are rising at 12-15% annually, and current recommendations
should be re-evaluated every 2-3 years.

Why city-tier-based and not income-based: a surgery costs the same
whether you earn 5 lakh or 50 lakh per year. Income-percentage
heuristics systematically under-insure low earners and over-insure
high earners. City-tier floors are calibrated to actual hospitalization
costs.

### FR-4: Compute Accident and Disability Cover Adequacy

Accident cover:
- Recommendation: 10x monthly income as personal accident cover
- This covers accidental death or permanent disability lump sum

Disability cover (if available):
- Recommendation: 50-60% of annual income as income replacement
  during disability period
- Note: standalone disability products are rare in India; the system
  should note this and suggest riders on existing term policies instead

These are simpler heuristics than life and health because the product
landscape is narrower and more standardized.

### FR-5: Compute Tax-Adjusted Effective Premium

For users on the OLD tax regime:
- Life insurance premiums qualify under Section 80C (up to 1.5 lakh
  combined with PPF, ELSS, etc.)
- Health insurance premiums qualify under Section 80D (25,000 for
  self/spouse/children + 25,000-50,000 for parents depending on age)
- Effective premium = Nominal premium x (1 - marginal tax rate)
- The system must estimate the user's marginal tax rate from their
  declared income

For users on the NEW tax regime:
- No 80C/80D benefit
- Effective premium = Nominal premium (no adjustment)

The system must clearly display both nominal and effective premium to
help users understand the tax benefit (or its absence).

Why this matters: post FY 2024-25, the new regime is default. Most
existing calculators still assume old regime deductions apply to
everyone, overstating the tax benefit for new-regime users.

### FR-6: Audit Existing Policies

For each existing policy the user enters, the system must evaluate:

Term life policies:
- Status: adequate/inadequate based on coverage gap
- No efficiency concern (term is the correct product for protection)

Endowment plans:
- Compute implied IRR based on: premium paid, policy tenure,
  maturity value (estimated using typical endowment returns of 4-6%)
- Compare against alternative: "term insurance + index fund" strategy
- Compute opportunity cost in rupees over remaining policy tenure
- Flag as: efficient / mixed / inefficient

ULIP policies:
- Same IRR analysis as endowment
- Additional flag: fund management charges typically 1.5-3% reduce
  effective returns further
- Flag as: efficient / mixed / inefficient

Health policies:
- Status: adequate/inadequate based on city-tier recommendation
- If below the minimum floor, quantify the gap

The system must NOT recommend surrendering existing policies — that
requires detailed analysis of surrender charges, lock-in periods,
and tax implications that are beyond scope. It should flag the
inefficiency and suggest "consult a fee-only advisor about this policy."

### FR-7: Budget-Constrained Gap Prioritization

Given the user's monthly insurance budget (a hard constraint), the
system must produce an ordered sequence of actions to close gaps.

Default priority logic:
1. Term life cover (if dependents exist and gap is large) — because
   dying without adequate cover is irreversible and catastrophic
2. Health cover (if below city-tier minimum) — because a single
   hospitalization can wipe out savings
3. Accident cover — because it is cheap (typically 200-500/month)
   and provides additional layer
4. Disability riders — because standalone products are rare; recommend
   as rider on term policy

Priority overrides:
- If user has no health cover at all, health moves to position 1
  (a health emergency is more probable than death for a young person)
- If user has no dependents, term life drops in priority
- If user already has adequate term but inadequate health, skip term

For each recommended action, the system must show:
- Product type
- Recommended sum assured
- Estimated monthly premium (illustrative range, not a real quote)
- Cumulative budget used so far
- Remaining budget after this action

If the total recommended coverage exceeds the budget, the system must:
- Show what can be covered within budget
- Show what remains uncovered
- Suggest the additional monthly amount needed to close all gaps

### FR-8: Generate Plain-English Explanation

The system must produce a personalized, plain-English summary of the
assessment. This summary must:
- Address the user by context (age, family situation)
- State the biggest gap first (lead with the most urgent finding)
- Explain each recommendation in non-technical language
- If existing policies are flagged as inefficient, explain why simply
- State the budget-constrained plan clearly
- End with the disclaimer

This explanation is generated by an LLM (Anthropic API) using a
structured prompt that includes the engine's numerical output.

The LLM must NEVER influence the numbers — it only explains them.

If the LLM is unavailable (API down, key missing, timeout, error),
the system must fall back to a template-based summary that covers
the same information in a fixed format. The system must never fail
because the LLM failed.

### FR-9: Expose via API

All functionality must be accessible via a REST API:
- A single primary endpoint that accepts the full user profile and
  returns the complete assessment (gaps, audit, plan, explanation)
- Proper input validation with clear error messages
- Proper HTTP status codes (200, 422 for validation errors, 500 for
  internal errors)
- OpenAPI/Swagger documentation auto-generated

### FR-10: Provide a Dashboard

A minimal Streamlit dashboard must provide:
- An input form matching the user profile schema
- A gap visualization (current cover vs recommended cover)
- The policy audit results with traffic-light indicators
- The budget-constrained plan as an ordered list
- The LLM-generated (or template) explanation
- The disclaimer footer

The dashboard must be simple and customer-first. No technical jargon
in the UI. The sophistication lives in the engine; the surface stays
clean.

## 5. Non-Functional Requirements

### NFR-1: Explainability
Every recommendation must be traceable to a stated formula, framework,
or decision rule. No black boxes. An interviewer (or regulator) asking
"why this number?" must get a concrete answer.

### NFR-2: Graceful Degradation
The system must function fully without the LLM. Template fallback must
cover every output the LLM would generate. The LLM is an enhancement,
not a dependency.

### NFR-3: Configuration over Hardcoding
All tunable parameters (discount rates, city-tier thresholds, priority
weights, tax brackets, medical inflation rates) must live in a
configuration file, not scattered as magic numbers in code.

### NFR-4: Input Validation
All user inputs must be validated with clear error messages. The system
must not crash or produce nonsense on malformed input.

### NFR-5: Disclaimer
Every output (API response and dashboard) must include the educational-
tool disclaimer. The system is not financial advice.

---

## 6. Out of Scope

The following are explicitly NOT part of this project:

- Specific product recommendations by insurer name or product name
- Real premium quotes (requires insurer API integration)
- PDF/document parsing for existing policies (manual input only)
- User authentication or data persistence (stateless tool)
- Machine learning models (adequacy is normative, not predictive)
- Mobile application (web dashboard only)
- Multi-language support
- Critical illness specific riders (simplified to health cover)
- NRI or non-Indian tax regime considerations
- Surrender value calculations for existing policies

Being explicit about scope boundaries is a maturity signal.

## 7. Success Criteria

The project is successful if:

1. A user can input their profile and receive a complete, personalized
   insurance adequacy assessment within 5 seconds
2. Every number in the output can be traced to a documented formula
3. The system works fully with the LLM off (template fallback)
4. The dashboard is understandable to a non-technical user
5. The codebase is clean enough that the developer (you) can explain
   any function's purpose and design rationale in an interview
6. The project is version-controlled with meaningful commit history
